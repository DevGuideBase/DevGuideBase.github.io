Audit logs and compliance checklist before Security Reviews

Run this checklist in order; each item assumes the previous one passed. It takes minutes and catches the failures that cost days.

  • Access verified: you can read and write everything this change touches.
  • Baseline captured: the current audit logs and compliance state is recorded somewhere recoverable.
  • Target confirmed: you know exactly which environment or branch you are changing.
  • Success signal defined: the command, log line or check that proves the change worked.
  • Rollback plan written: the one command (or commit revert) that undoes everything.
  • Reviewer lined up: someone else knows what good looks like for this change.
  • Documentation updated: the setup notes reflect reality after the change.

GitHub Enterprise commands and configuration for audit logs and compliance

Here is the concrete tooling for the job. Everything in the block ships with GitHub Enterprise or its standard toolchain — no extra installs, no helper scripts to trust.

# Org-level policy for audit logs and compliance (Enterprise Cloud)
gh api -X PATCH /orgs/audit-logs-and-compliance-org \
  -F members_can_create_repositories=false \
  -F default_repository_permission=read \
  -F web_commit_signoff_required=true

Treat the snippet as a template rather than a prescription: the sequence matters more than the exact values, which will differ per repository and environment.

How Security Reviews changes the approach

Scale changes failure modes. Under formal security review, where every decision needs evidence, a audit logs and compliance mistake that would annoy one developer can block an entire team, so the checklist below errs on the side of boring, reversible steps.

  • Agree the review path for audit logs and compliance changes before the first one lands — security reviews amplifies every ambiguity.
  • Keep GitHub Enterprise versions, tooling and configuration identical across the environments this scope covers.
  • Write the rollback step down before the change, not after the failure.
  • Prefer reversible, incremental rollout over one large switch whenever the option exists.

Common mistakes and how to avoid them

Before you implement anything above, make sure you are not stepping on one of these well-known rakes:

  • Not streaming audit logs to SIEM, so investigations lack history.
  • Mixing personal and service accounts in the same IdP lifecycle.
  • Upgrading Enterprise Server without a tested restore drill.
  • Granting enterprise-wide PAT scopes when repo-level tokens suffice.
  • Configuring branch protections per repo instead of enforced rulesets.

If you recognise your own setup in three or more of these, stop adding features and spend a day on remediation first. The fixes are usually small; the incidents they prevent are not.

Best practices checklist

Run down this checklist before you call the work done. It compresses everything above into the checks that actually catch problems:

  • Enforce SSO + SCIM with EMU where regulation requires it.
  • Adopt repository rulesets org-wide with exceptions documented.
  • Stream audit logs to Splunk/Sentinel; alert on privilege changes.
  • Standardize self-hosted runner images via IaC.
  • Quarterly access reviews keyed to SCIM groups.
  • Pin enterprise policy for {TOPIC} in version control with approvals.

Adapt the list to your context, but do not shrink it below the first four items — those cover the failure modes with the worst cost-to-likelihood ratio in audit logs and compliance work.

Frequently Asked Questions

How long does it take to check audit logs and compliance for security reviews?

Most teams need under an hour the first time they follow this procedure, mostly spent on the preparation and verification steps. Once the steps are scripted or templated for GitHub Enterprise, repeat runs typically take minutes rather than hours.

Which GitHub Enterprise version do I need for audit logs and compliance?

Use the same major version everywhere — local machines, build agents and production hosts. Version drift between environments is the single most common reason audit logs and compliance behaves differently in security reviews than on a developer laptop.

Can I automate audit logs and compliance instead of following these steps by hand?

Yes, and for security reviews you almost certainly should. Every step in this guide maps cleanly to a script or pipeline job; the commands section above is a starting skeleton. Keep one human-readable checklist even after automation, for audits and incident review.

What is the fastest way to verify audit logs and compliance worked?

Define the success signal before you start — a command that exits zero, a log line, or a passing check — then run it immediately after the change. If you cannot articulate that signal yet, that is the real blocker, not the audit logs and compliance mechanics.
